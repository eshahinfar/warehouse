# سیستم انبارداری — نسخه تحت شبکه

نسخه‌ای از سیستم انبارداری که روی یک کامپیوتر در شبکه داخلی کارخانه اجرا می‌شود
و همکاران با مرورگر خودشان (بدون نصب هیچ برنامه‌ای) به آن وصل می‌شوند.

**بدون نیاز به npm install، بدون سرور جداگانه، بدون اینترنت.**
تنها با ماژول‌های داخلی Node.js نوشته شده (`node:sqlite`, `node:http`, `node:crypto`).

---

## ۱. پیش‌نیاز

فقط **Node.js نسخه ۲۲.۵ یا بالاتر** روی کامپیوتر میزبان (سروری که همیشه روشن
می‌ماند) نصب باشد. دانلود: https://nodejs.org (نسخه LTS یا جدیدتر)

بررسی نسخه نصب‌شده:
```
node --version
```

## ۲. اجرا

```
cd warehouse-server
node src/server.js
```

در ترمینال آدرس‌هایی مثل این نمایش داده می‌شود:
```
روی همین کامپیوتر : http://localhost:8080
روی شبکه داخلی    : http://192.168.1.23:8080
```

- روی خود کامپیوتر میزبان: `http://localhost:8080` را باز کنید.
- روی سایر کامپیوترها/تبلت‌ها/موبایل‌های همان شبکه: آدرس دوم
  (`http://192.168.1.23:8080` یا هر عددی که سیستم شما نشان می‌دهد) را در
  مرورگر وارد کنید.

## ۳. ورود اولیه

حساب مدیر پیش‌فرض در اولین اجرا خودکار ساخته می‌شود:
- **نام کاربری:** `admin`
- **رمز عبور:** `111111`

**تغییر این رمز در اولین ورود اجباری است و توسط خود سرور اعمال می‌شود** —
تا وقتی رمز عوض نشود، تمام مسیرهای دیگر سامانه پاسخ ۴۰۳ می‌دهند. رمز جدید
باید حداقل ۸ کاراکتر باشد و از فهرست رمزهای بدیهی نباشد.

اگر می‌خواهید رمز اولیه چیز دیگری باشد (مثلاً در استقرار اینترنتی)، پیش از
اولین اجرا آن را در `config.json` یا متغیر محیطی تعیین کنید:
```json
{ "initialAdminPassword": "یک-رمز-قوی-دلخواه" }
```

## ۴. اجرای دائمی (تا با ری‌استارت کامپیوتر خاموش نشود)

### ویندوز
ساده‌ترین روش: از ابزار [NSSM](https://nssm.cc) برای ثبت به‌عنوان سرویس ویندوز
استفاده کنید، یا یک فایل `start.bat` بسازید و آن را به «Startup» ویندوز اضافه
کنید:
```bat
cd /d C:\warehouse-server
node src\server.js
```

### لینوکس
با `systemd` به‌عنوان سرویس ثبت کنید (نمونه فایل سرویس در ادامه)، یا با `pm2`
(در صورت وجود اینترنت برای نصب یک‌باره).

## ۵. پشتیبان‌گیری

تمام داده‌ها در یک فایل است: `data/warehouse.db`
سرور خودش هر ۲۴ ساعت (قابل تنظیم) یک نسخه‌ی کامل و سازگار در `backups/`
می‌سازد و مدیر سیستم می‌تواند از تب «حسابرسی» هر لحظه پشتیبان فوری بگیرد.

⚠️ **نسخه‌ی پشتیبانی که روی همان دیسک سرور بماند، در خرابی دیسک هیچ کمکی
نمی‌کند** — داده و پشتیبان با هم از بین می‌روند. یک مسیر دوم تنظیم کنید تا
نسخه‌ی آینه‌ای هم آن‌جا ذخیره شود.

### ۵.۱. تنظیم مسیر آینه‌ای

در `config.json`:

**ویندوز — پوشه‌ی اشتراکی روی سرور/NAS دیگر (توصیه‌شده):**
```json
{ "backupMirrorDir": "\\\\server-backup\\warehouse" }
```
در JSON هر بک‌اسلش باید دوتایی نوشته شود، پس مسیر واقعی
`\\server-backup\warehouse` این‌طور نوشته می‌شود.

⚠️ **درایو نگاشته‌شده (`Z:`) ننویسید.** وقتی سرور به‌عنوان سرویس ویندوز اجرا
می‌شود، درایوهای نگاشته‌شده‌ی کاربر برایش وجود ندارند و پشتیبان‌گیری بی‌صدا
شکست می‌خورد. همیشه مسیر کامل UNC بنویسید و سرویس را با کاربری اجرا کنید که
به آن اشتراک اجازه‌ی نوشتن دارد.

**ویندوز — هارد اکسترنال یا فلش دائمی:**
```json
{ "backupMirrorDir": "E:\\warehouse-backups" }
```

**لینوکس — پوشه‌ی شبکه یا دیسک دوم:**
```json
{ "backupMirrorDir": "/mnt/backup-share/warehouse" }
```
مطمئن شوید که mount در `/etc/fstab` ثبت شده تا بعد از ری‌استارت هم برقرار باشد.

### ۵.۲. بررسی سلامت پشتیبان‌گیری

سرور هنگام راه‌اندازی مسیر آینه‌ای را با یک نوشتن آزمایشی بررسی می‌کند و اگر
قابل نوشتن نباشد، یک هشدار برجسته در ترمینال چاپ می‌کند (پشتیبان‌گیری محلی
متوقف نمی‌شود).

مدیر سیستم می‌تواند هر لحظه از **تب «حسابرسی» → کارت «وضعیت پشتیبان‌گیری»**
ببیند آخرین نسخه کِی ساخته شده، کجا ذخیره شده و آیا مسیر آینه‌ای هنوز در
دسترس است. همان‌جا دکمه‌ی «پشتیبان‌گیری فوری» هم هست.

این کارت مخصوصاً برای حالتی است که پوشه‌ی شبکه ماه‌ها پیش قطع شده و کسی
متوجه نشده باشد — چیزی که فقط با نگاه‌کردن به لاگ ترمینال معلوم نمی‌شود.

### ۵.۳. بازیابی از نسخه پشتیبان

هر فایل پشتیبان یک پایگاه‌داده‌ی SQLite کامل و مستقل است:
۱. سرور را متوقف کنید.
۲. فایل پشتیبان را به `data/warehouse.db` تغییر نام دهید و جایگزین کنید
   (فایل‌های `warehouse.db-wal` و `warehouse.db-shm` قدیمی را پاک کنید).
۳. سرور را دوباره اجرا کنید.
۴. از تب حسابرسی یک بار «بررسی تطبیق موجودی» بگیرید.

## ۶. فایروال

اگر کامپیوترهای دیگر نمی‌توانند وصل شوند، فایروال ویندوز/لینوکس را برای پورت
`8080` (یا هر پورتی که با متغیر محیطی `PORT` تنظیم کرده‌اید) باز کنید.

## ۷. تغییر پورت

```
PORT=9000 node src/server.js
```

## ۸. اتصال اینترنتی (دسترسی از خارج کارخانه با دامنه ثابت)

این بخش سرور را از حالت «فقط شبکه داخلی» به حالت **HTTPS واقعی و امن** برای
دسترسی از طریق اینترنت (با دامنه‌ای مثل `warehouse.company.com`) تبدیل می‌کند.
گواهی SSL از [Let's Encrypt](https://letsencrypt.org) — مرجع صدور گواهی رایگان
و معتبر جهانی — با ابزار استاندارد `certbot` دریافت می‌شود؛ هیچ بسته npm یا
سرویس شخص‌ثالث پولی لازم نیست.

### ۸.۱. تنظیم دامنه

در پنل مدیریت دامنه‌ی خود، یک رکورد `A` بسازید که به **آی‌پی عمومی کارخانه**
اشاره کند:
```
Type: A
Name: warehouse   (یا هر ساب‌دامنه‌ای که می‌خواهید، یا @ برای ریشه دامنه)
Value: <آی‌پی عمومی شما>
```
برای پیدا کردن آی‌پی عمومی فعلی، از خود کامپیوتر سرور آدرس زیر را باز کنید:
`https://api.ipify.org`

⚠️ اگر اینترنت کارخانه آی‌پی عمومی ثابت ندارد (اکثر اینترنت‌های خانگی/اداری
همین‌طورند)، باید یا از ISP آی‌پی ثابت بگیرید یا از یک سرویس DDNS رایگان
(مثل [DuckDNS](https://www.duckdns.org) یا [No-IP](https://www.noip.com))
استفاده کنید که آدرس دامنه را خودکار به‌روز نگه می‌دارد.

### ۸.۲. باز کردن پورت‌ها روی روتر کارخانه

در تنظیمات روتر (Port Forwarding)، دو پورت را به آی‌پی داخلی کامپیوتر سرور
هدایت کنید:
```
پورت خارجی 80  → آی‌پی داخلی سرور : پورت 80    (لازم برای صدور/تمدید گواهی)
پورت خارجی 443 → آی‌پی داخلی سرور : پورت 443   (ترافیک اصلی HTTPS)
```

### ۸.۳. دریافت گواهی SSL رایگان با certbot

نصب certbot (یک‌بار، نیاز به اینترنت):
- **لینوکس (Ubuntu/Debian):** `sudo apt install certbot`
- **ویندوز:** نسخه‌ی [Certbot for Windows](https://certbot.eff.org) را نصب کنید،
  یا ساده‌تر: certbot را از طریق WSL (لینوکس داخل ویندوز) اجرا کنید.

سپس (پیش از اجرای این دستور، سرور را در حالت `lan` روی پورت ۸۰ خاموش نگه دارید
تا پورت ۸۰ آزاد باشد، یا از حالت webroot استفاده کنید که تداخلی ندارد):

```
sudo certbot certonly --standalone -d warehouse.company.com
```

گواهی در مسیر زیر ذخیره می‌شود:
```
/etc/letsencrypt/live/warehouse.company.com/fullchain.pem
/etc/letsencrypt/live/warehouse.company.com/privkey.pem
```

### ۸.۴. تنظیم config.json

فایل `config.example.json` را کپی کرده و به‌نام `config.json` در ریشه‌ی
پروژه ذخیره کنید، سپس این مقادیر را پر کنید:

```json
{
  "mode": "https",
  "httpPort": 80,
  "httpsPort": 443,
  "domain": "warehouse.company.com",
  "certPath": "/etc/letsencrypt/live/warehouse.company.com/fullchain.pem",
  "keyPath": "/etc/letsencrypt/live/warehouse.company.com/privkey.pem"
}
```

سپس سرور را اجرا کنید:
```
sudo node src/server.js
```
(روی لینوکس، اتصال به پورت‌های زیر ۱۰۲۴ نیاز به دسترسی root/sudo دارد. روی
ویندوز معمولاً چنین محدودیتی وجود ندارد.)

از این پس سیستم روی `https://warehouse.company.com` از هر نقطه‌ای با اینترنت
در دسترس است.

### ۸.۵. تمدید خودکار گواهی

گواهی‌های Let's Encrypt هر ۹۰ روز منقضی می‌شوند. برای تمدید خودکار، یک
Cron Job (لینوکس) یا Task Scheduler (ویندوز) هر روز این دستور را اجرا کند:

```
certbot renew --webroot -w /path/to/warehouse-server/acme-webroot
```

سرور خودش هر ساعت بررسی می‌کند که آیا فایل گواهی تازه‌تر شده؛ در این صورت
**بدون نیاز به ری‌استارت** گواهی جدید را جایگزین می‌کند (کاربران متصل قطع
نمی‌شوند).

### ۸.۶. لایه‌های امنیتی فعال در حالت اینترنتی

از آن‌جا که این حالت سرور را روی اینترنت عمومی باز می‌کند (نه فقط شبکه
داخلی)، این محافظت‌ها به‌صورت خودکار فعال هستند:

| محافظت | توضیح |
|---|---|
| HTTPS اجباری | تمام ترافیک HTTP به‌طور خودکار به HTTPS هدایت می‌شود |
| HSTS | به مرورگر می‌گوید همیشه از HTTPS استفاده کند (ضدحملات downgrade) |
| محدودسازی تلاش ورود | بعد از ۵ تلاش ناموفق ورود از یک آی‌پی، آن آی‌پی به‌مدت ۱۵ دقیقه مسدود می‌شود (قابل تنظیم در config.json) |
| بررسی Origin | درخواست‌های تغییردهنده (ثبت/ویرایش/حذف) فقط از خودِ سایت پذیرفته می‌شوند (ضد CSRF) |
| کوکی Secure + HttpOnly | کوکی نشست فقط روی HTTPS ارسال می‌شود و از جاوااسکریپت قابل خواندن نیست |
| هدرهای امنیتی | X-Frame-Options، Content-Security-Policy و... در هر پاسخ ارسال می‌شوند |

⚠️ **توصیه مهم:** این محافظت‌های سطح برنامه، جایگزین محافظت‌های سطح شبکه
نیستند. توصیه می‌شود علاوه بر این‌ها:
- فایروال سیستم‌عامل فقط پورت‌های ۸۰ و ۴۴۳ را باز نگه دارد (نه هیچ پورت
  دیگری، مثل همان پورت SSH/RDP مدیریتی که باید جداگانه محافظت شود)
- رمز عبور هر کاربر قوی و منحصربه‌فرد باشد (این‌جا دیگر رمز پیش‌فرض یکسان
  قابل قبول نیست، چون سطح حمله از «هرکسی در کارخانه» به «هرکسی در اینترنت»
  تغییر کرده است)
- به‌طور دوره‌ای از فایل `data/warehouse.db` پشتیبان بگیرید

### ۸.۷. بازگشت به حالت شبکه داخلی

کافی است در `config.json` مقدار `"mode"` را به `"lan"` برگردانید (یا فایل
config.json را پاک کنید تا پیش‌فرض `lan` اعمال شود).

## سطوح دسترسی (نقش‌ها)

| نقش | دسترسی |
|---|---|
| **مدیر سیستم** | همه‌چیز، از جمله مدیریت کاربران، ویرایش/حذف اسناد، حذف کالا |
| **انباردار** | ثبت رسید ورود/حواله خروج/مرجوعی، مدیریت امانت ابزار و تعمیرگاه، مدیریت کامل درخواست‌ها (ایجاد/ویرایش/لغو/حذف/تولید خودکار)، مشاهده گزارش‌ها |
| **درخواست‌دهنده** | فقط ثبت و مشاهده درخواست کالا، مشاهده کالاها و داشبورد |
| **ناظر** | فقط مشاهده (کالاها، درخواست‌ها، گزارش‌ها، داشبورد) — بدون هیچ امکان ثبت/ویرایش |

نکته امنیتی: این محدودیت‌ها **در سمت سرور** اعمال می‌شوند (نه فقط با پنهان
کردن دکمه‌ها در رابط کاربری)، بنابراین با ابزار توسعه‌دهنده مرورگر قابل دور
زدن نیستند.

## وضعیت فعلی سیستم

این نسخه، **پایه و اسکلت کامل معماری** را پیاده‌سازی کرده تا الگوی کلی کار
تأیید شود:

✅ پایگاه داده SQLite با تمام جدول‌های لازم (کالاها، اسناد، درخواست‌ها،
   امانت ابزار، تعمیرگاه، لاگ حسابرسی، کاربران)
✅ سیستم ورود و نشست (Session) با رمزنگاری امن (scrypt)
✅ چهار سطح دسترسی: مدیر سیستم / انباردار / درخواست‌دهنده / ناظر
✅ کنترل دسترسی **در سمت سرور** (نه فقط ظاهر برنامه — قابل دور زدن نیست)
✅ ماژول کامل مدیریت کالاها (افزودن با ثبت خودکار سند رسید موجودی اولیه،
   ویرایش، حذف با الزام ثبت دلیل و درج در لاگ حسابرسی)
✅ داشبورد خلاصه وضعیت
✅ لاگ حسابرسی
✅ مدیریت کاربران (افزودن، فعال/غیرفعال‌سازی، تغییر نقش)
✅ رابط کاربری وب پایه (صفحه ورود + این بخش‌ها)
✅ پشتیبانی از HTTPS واقعی برای دسترسی اینترنتی با دامنه ثابت (گواهی رایگان
   Let's Encrypt، تمدید خودکار بدون قطعی، ری‌دایرکت خودکار HTTP→HTTPS)
✅ سخت‌سازی امنیتی برای حالت اینترنتی: محدودسازی تلاش ورود، بررسی Origin
   (ضدCSRF)، هدرهای امنیتی استاندارد (HSTS، CSP، X-Frame-Options)، کوکی
   نشست با پرچم Secure+HttpOnly
✅ رسید ورود / حواله خروج / مرجوعی — با شماره‌گذاری خودکار و بازشماری
   پیوسته پس از حذف سند (دقیقاً مطابق نسخه آفلاین)
✅ امانت ابزار — تحویل/بازگشت، تشخیص خودکار وضعیت (مفقود → کسر موجودی،
   نیازمند تعمیر → ایجاد خودکار رکورد تعمیرگاه)
✅ تعمیرگاه — ارسال، تکمیل با نام تعمیرکار و تأییدکننده، کسر خودکار موجودی
   در صورت اسقاط
✅ درخواست کالا — ثبت، ویرایش، لغو، حذف (با بازشماری)، تولید خودکار برای
   کالاهای کم‌موجود
✅ مدیریت اسناد — ویرایش/حذف هر سند (فقط مدیر سیستم)، با الزام ثبت دلیل و
   بازشماری خودکار پس از حذف
✅ گزارش‌ها — کمبود/هشدار، کاردکس کالا (با موجودی تجمعی)، گزارش سفارشی
✅ تقویم هجری شمسی در تمام فیلدهای تاریخ رابط کاربری وب
✅ به‌روزرسانی آنی بین کاربران با WebSocket دست‌ساز (بدون بسته npm، طبق
   استاندارد RFC 6455) — به‌محض ثبت/ویرایش/حذف یک سند توسط هر کاربر، تب
   فعال سایر کاربران بلافاصله تازه‌سازی می‌شود؛ همراه با polling هر ۳۰
   ثانیه به‌عنوان پشتیبان در صورت قطع موقت اتصال
✅ آیکون‌های SVG درون‌خطی در سراسر رابط کاربری (بدون کتابخانه/فونت خارجی)
✅ چاپ رسمی رسیدها (ورود/خروج/مرجوعی/امانت/تعمیر) و گزارش‌ها (کمبود،
   کاردکس) — دکمه «چاپ» بلافاصله پس از هر ثبت موفق ظاهر می‌شود؛ در پنجره
   چاپ مرورگر، «Save as PDF» هم به‌طور بومی در دسترس است
✅ پشتیبان‌گیری خودکار زمان‌بندی‌شده از پایگاه‌داده (پیش‌فرض: هر ۲۴ ساعت،
   نگه‌داری ۳۰ نسخه آخر، حذف خودکار نسخه‌های قدیمی‌تر) با دستور استاندارد
   SQLite `VACUUM INTO` که بدون قفل‌کردن دیتابیس یا قطعی سرویس اجرا می‌شود

## تنظیمات پشتیبان‌گیری خودکار

در `config.json` قابل تنظیم است:
```json
{
  "backupEnabled": true,
  "backupIntervalHours": 24,
  "backupKeepCount": 30,
  "backupDir": "./backups",
  "backupMirrorDir": ""
}
```
نسخه‌های پشتیبان در پوشه `backups/` با نام‌گذاری زمان‌دار ذخیره می‌شوند
(مثل `warehouse-backup_2026-08-21_03-34.db`) و هرکدام یک فایل SQLite کامل
و مستقل است که با کپی ساده قابل بازیابی است (جایگزینی فایل `data/warehouse.db`
هنگام خاموش بودن سرور).

## نسخه ۲ — فهرست اصلاحات

این نسخه پس از یک بازبینی کامل کد اصلاح شده است. تغییرات مهم:

### اشکالات بازدارنده
1. **کار نکردن سامانه در شبکه داخلی.** بررسی Origin فقط `localhost` را مجاز
   می‌دانست، بنابراین هر مرورگری که با آدرس شبکه (`http://192.168.1.23:8080`)
   وصل می‌شد حتی نمی‌توانست وارد شود. حالا همه‌ی آی‌پی‌های محلی سرور خودکار
   مجاز می‌شوند و هر ۱۰ دقیقه (برای تغییر آی‌پی در DHCP) بازخوانی می‌شوند.
   آدرس‌های مجاز هنگام اجرا در ترمینال چاپ می‌شوند.
2. **واگرایی موجودی.** حذف سند از `Math.max(0, ...)` استفاده می‌کرد و موجودی
   بی‌صدا با دفتر اسناد اختلاف پیدا می‌کرد. حالا موجودی فقط از یک مسیر
   کنترل‌شده تغییر می‌کند که هرگز اجازه‌ی منفی شدن نمی‌دهد، و ابزار
   «تطبیق موجودی» (تب حسابرسی) هر اختلاف احتمالی را نشان داده و اصلاح می‌کند.
3. **شماره‌گذاری مجدد اسناد.** با حذف هر سند، تمام اسناد هم‌نوع دوباره
   شماره‌گذاری می‌شدند؛ نتیجه این بود که لاگ حسابرسی به سند دیگری اشاره
   می‌کرد و رسیدهای چاپ‌شده در واحدها با سامانه نمی‌خواند. **حذف سند حالا
   جای خود را به «ابطال» داده است:** شماره سند برای همیشه محفوظ می‌ماند، سند
   با برچسب «باطل» در سوابق و کاردکس دیده می‌شود و اثرش بر موجودی برگردانده
   می‌شود — دقیقاً مثل دفتر انبار کاغذی که سند باطل خط می‌خورد، پاره نمی‌شود.
   همین منطق برای درخواست‌ها (لغو)، امانت و تعمیر هم اعمال شد.

### اعتبارسنجی و یکپارچگی داده
4. اعتبارسنجی متمرکز: تعداد باید عدد صحیح مثبت با سقف منطقی باشد (قبلاً
   «۲.۷ عدد پیچ» پذیرفته می‌شد) و تاریخ باید واقعاً در تقویم وجود داشته باشد
   (قبلاً `not-a-date` ذخیره می‌شد).
5. همه‌ی عملیات چندمرحله‌ای داخل تراکنش پایگاه‌داده اجرا می‌شوند؛ قطع برق یا
   خطا وسط کار، نیمه‌عملیات روی دیسک نمی‌گذارد.
6. **حذف کالا دیگر تاریخچه را پاک نمی‌کند.** کالای دارای سند «بایگانی»
   می‌شود (از فهرست‌ها خارج، سوابق دست‌نخورده)؛ فقط کالای بدون هیچ سندی
   واقعاً حذف می‌شود. کالای دارای امانت باز اصلاً حذف نمی‌شود.
7. **موجودی قابل تخصیص.** ابزاری که امانت داده شده یا در تعمیرگاه است دیگر
   «موجود» شمرده نمی‌شود؛ گزارش کمبود و درخواست خودکار بر همین مبنا کار
   می‌کنند و تحویل/ارسال بیش از موجودی واقعی رد می‌شود.
8. ویرایش و ابطال رکوردهای امانت و تعمیر اضافه شد (قبلاً اصلاح یک اشتباه
   تایپی فقط با دست بردن در فایل پایگاه‌داده ممکن بود).

### امنیت
9. عبور از پوشه‌ی عمومی در سرو فایل استاتیک بسته شد (بررسی مسیر با
   جداکننده انجام می‌شود، نه صرفاً پیشوند رشته‌ای).
10. تغییر رمز اولیه سمت سرور اجباری شد؛ حداقل طول رمز از ۴ به ۸ رسید و
    رمزهای بدیهی رد می‌شوند. تغییر یا بازنشانی رمز، نشست‌های باز آن کاربر
    را می‌بندد.
11. محدودیت تلاش ورود در پایگاه‌داده ذخیره می‌شود و با ری‌استارت سرور باز
    نمی‌شود.
12. سیاست CSP سخت‌گیر شد (`script-src 'self'` بدون `unsafe-inline`)؛ برای
    این کار همه‌ی `onclick`های درون‌خطی رابط کاربری به شنونده‌ی رویداد
    تبدیل شدند.
13. هدر `X-Forwarded-For` فقط در صورت تنظیم صریح `trustProxy` معتبر شمرده
    می‌شود (وگرنه هر کاربری می‌توانست با جعل آن محدودیت ورود را دور بزند).

### کارایی و بهره‌برداری
14. فهرست اسناد صفحه‌بندی شد و جست‌وجو به پایگاه‌داده منتقل شد (قبلاً همه‌ی
    ردیف‌ها خوانده و در جاوااسکریپت فیلتر می‌شدند).
15. نام فایل پشتیبان تا ثانیه دقت دارد (قبلاً دو راه‌اندازی در یک دقیقه
    باعث خطای `output file already exists` می‌شد) و امکان نسخه‌ی آینه‌ای در
    مسیر دوم اضافه شد.
16. فایل‌های استاتیک هدر `ETag` می‌گیرند؛ پس از به‌روزرسانی سامانه، مرورگرها
    دیگر نسخه‌ی قدیمی `app.js` را نگه نمی‌دارند.
17. مهاجرت خودکار پایگاه‌داده: نسخه‌های قبلی بدون از دست رفتن داده ارتقا
    می‌یابند و شماره سند تکراری (به‌جامانده از باگ شماره‌گذاری) هنگام اجرا
    گزارش می‌شود.

### افزوده‌های تکمیلی
18. **تاریخ موجودی اولیه** هنگام تعریف کالا قابل انتخاب شد. قبلاً سند موجودی
    اولیه همیشه تاریخ امروز می‌خورد؛ اگر اسناد قبلی با تاریخ گذشته وارد
    می‌شدند، ستون مانده در کاردکس موقتاً منفی نشان می‌داد. تاریخ آینده رد
    می‌شود و اگر خالی بماند، مثل قبل امروز در نظر گرفته می‌شود.
19. **پایش پشتیبان‌گیری**: بررسی نوشتن‌پذیری مسیر آینه‌ای هنگام راه‌اندازی،
    هشدار برجسته در صورت خرابی (با راهنمای UNC برای سرویس ویندوز)، و کارت
    «وضعیت پشتیبان‌گیری» در تب حسابرسی.
